Reproduced this on one RTX PRO 6000 Blackwell (Server Edition, sm_120) with the official v0.31.0 image, so TP2 isn't needed. I used `gaunernst/DeepSeek-V2-Lite-Chat-FP8`, which has the same MLA decode shape (kv_lora_rank 512, qk_rope_head_dim 64) and fits on one GPU. The trigger is the fp8 KV cache: with `kv_cache_dtype=auto` the same model serves on `TRITON_MLA`, and with `--kv-cache-dtype fp8` it fails at boot with the exact `Required: 102400, Hardware limit: 101376`.

This is the same overflow as #53748 (reported on GB10), and three PRs target it: #54013, #60173 and #61068. I applied each one to v0.31.0 and ran the same fp8 config:

| Variant | Result | GSM8K-100 (5-shot, chat API) |
|---|---|---|
| auto KV, no patch | serves | 0.70 |
| fp8 KV, no patch | OutOfResources at boot | - |
| fp8 KV + #60173 | serves | 0.71 |
| fp8 KV + #54013 | serves | 0.68 |
| fp8 KV + #61068 | serves | 0.69 |

All three remove the overflow, and GSM8K stays inside noise of the auto KV control (100 questions, so roughly +/-0.05). #54013 and #60173 pick the stage count up front from the device limit; #61068 catches the OutOfResources and retries with fewer stages, so it also covers shapes nobody has measured yet. If a maintainer picks one, I can rerun it on the final revision.
